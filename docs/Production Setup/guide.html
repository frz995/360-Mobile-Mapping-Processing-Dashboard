1About this system

What GeoSphere 360 is, how it is put together, and what it does not do.

1.1 What it is

GeoSphere 360 is a browser-based WebGIS dashboard for 360 degree mobile-mapping survey data, together with a small set of on-premises services that connect it to a survey NAS and to four photogrammetry workstations.

A surveyor captures 360 imagery and GNSS/IMU telemetry on a vehicle rig. Operator PCs run desktop photogrammetry software to blur, stitch, enhance and retouch the imagery. The dashboard coordinates that work: it shows which subgrid has been captured, what stage each workstation has reached, which frames failed quality inspection, and what has been published to the WebGIS layer.

1.2 What it is not

This distinction drives hardware purchasing, so it is stated plainly and early.

No server-side image processing

The platform does not run a server-side image pipeline. There is no GPU worker, no batch enhancement queue, and no image-processing job store.

  • Panorama quality analysis — sharpness, privacy-blur verification, obstruction and glare detection — runs in the operator's browser on a WebGL shader path, with a CPU fallback.
  • Image editing — blurring, stitching, enhancement, nadir removal — is performed by operators in desktop software on the four workstations. The dashboard observes their progress; it does not drive them.

You do not need: an NVIDIA GPU, CUDA, PyTorch, OpenCV, a GPU workstation, or a GPU queue service. Standard office hardware is sufficient. Section 2.3 gives the actual list.

1.3 Architecture

The system splits into a cloud half, which the client's users reach over HTTPS, and an on-premises half that never touches the public internet. A Cloudflare Tunnel bridges them.

Design principle

The database is the single source of truth. The NAS is treated as read-only by the dashboard: the worker rejects any path that resolves outside its configured base, so a malformed request cannot reach unrelated files on the client network.

3Database

Project creation, PostGIS, the migration sequence and verification.

3.1 Create the project

Supabase Cloud — create a project in your organisation. Self-hosted — run the Supabase Docker stack. Record the project URL and the anon / publishable key; you will enter them in both the browser-facing and the server-facing configuration.

3.2 Enable PostGIS before the first migration

Ordering trap — enable PostGIS first

The first migration creates a summary view only if PostGIS already exists. If it is absent at that moment the view is silently skipped, and PostGIS is only installed later by migration 0012.

Do this first: Supabase → Database → Extensions → postgis → Enable. Then apply the migrations.

How to run them

Fastest path: run the single consolidated bundle supabase/bootstrap.sql (generated via npm run migrations:bootstrap). Paste and run in the Supabase SQL editor in one step.

3.4 Verify the schema landed

-- security functions present (expect: can, get_app_role, is_role, normalize_role)
select proname from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'sec' order by 1;

-- PostGIS enabled
select extname from pg_extension where extname = 'postgis';

-- row-level security actually enabled on the privileged tables (expect several rows)
select relname, relrowsecurity from pg_class
 where relnamespace = 'public'::regnamespace and relrowsecurity
 order by 1;

-- the views the application reads
  select table_name from information_schema.views
   where table_schema = 'public'
     and table_name in ('panoramas_view', 'panoramas_subgrid_summary');

  -- GATE: directory-authoritative role resolver in place (expect NEW)
  -- OLD means 0030 did not apply, and Disable does not revoke access
  select case when prosrc like '%not Active%'
           then 'NEW' else 'OLD' end as resolver
    from pg_proc where proname = 'get_app_role';

  -- RLS gaps: expect ZERO rows in both (spatial_ref_sys is PostGIS's own)
  select c.relname as rls_missing
    from pg_class c join pg_namespace n on n.oid = c.relnamespace
   where n.nspname = 'public' and c.relkind = 'r'
     and not c.relrowsecurity and c.relname <> 'spatial_ref_sys';

  -- RLS on but ZERO policies = deny-all. Expect ZERO rows.
  select c.relname as no_policies
    from pg_class c join pg_namespace n on n.oid = c.relnamespace
   where n.nspname = 'public' and c.relkind = 'r' and c.relrowsecurity
     and not exists (select 1 from pg_policies p
       where p.schemaname = 'public' and p.tablename = c.relname);

If panoramas_subgrid_summary is missing, PostGIS was not installed when migration 0001 ran. Enable PostGIS and re-run the view block from 0001 (Section 3.2).

If the resolver reads OLD, the sequence stopped before 0030 — most often because psql was run with ON_ERROR_STOP=1 and stopped at 0004. Re-run the sequence tolerantly, then 0030. If either RLS query returns rows, apply 0031.

4Storage buckets

Which buckets to create, and the privacy decision you must make consciously.

4.1 Panorama bucket — create it manually, and make it public

No migration creates the panorama bucket. Create it yourself: Supabase → Storage → New bucket.

SettingValue
NameMMS_PIC
Public bucketON
Storage Modes: Public vs Enterprise Private

Public Bucket (Default): Builds direct public CDN/storage URLs for zero API signing latency during public survey viewing.

Enterprise Private Bucket: Fully supported via isPrivateBucket in Admin Settings. The platform pre-signs and caches signed tokens in memory with a 50-minute safe validity window, resolving images through authenticated storage endpoints without viewer interruption.

Privacy decision — make it consciously

With a public bucket, the object path is the only protection on an image, and survey filenames typically encode the subgrid and frame index. If your imagery is confidential, agree an alternative with your integrator before go-live: either keep raw imagery off this bucket and serve previews through the NAS worker, or request the signed-URL capability as a development item.

4.2 Road-analysis geometry bucket — automatic

Migration 0021 creates a bucket named road-analysis-geometry with private access and authenticated-only storage policies. No action is required. If it is missing, Road Analysis geometry saves fall back to browser-local storage, so nothing breaks visibly — check for it if layer saves appear not to persist.

4.3 A bucket you do not need

Some older documentation instructs you to create a vector_layers bucket. The current code never reads or writes it. Skip it.

5First administrator

Bootstrapping the first account, which cannot be done from inside the application.

5.1 Automated Provisioning & Manual Fallback

Turnkey Provisioning CLI (Recommended)

Provision the initial administrator in a single step using the automated script: npm run admin:seed (or provide --email and --password arguments). Then verify full system and database readiness with npm run doctor.

If you prefer manual configuration in the Supabase Dashboard, follow the four steps below.

5.2 The four steps

1
Create the authentication user

In the Supabase dashboard go to Authentication → Users → Add user. Enter an email address and password, or send an invitation. Note the address — it is used in step 3.

2
Set the role metadata

Open the new user and edit their metadata. Set App Metadata first, because that is what lands in the JSON Web Token and is the fastest path to a working administrator.

{ "role": "Administrator" }

Set User Metadata to the same value, because the dashboard reads User Metadata before App Metadata.

3
Insert the directory row
insert into public.user_accounts (name, email, role, status)
values ('<Full Name>', '<email>', 'Administrator', 'Active')
on conflict (email) do update
  set role = 'Administrator', status = 'Active';
4
Verify before signing in
select sec.get_app_role();   -- must return: Administrator

If it returns Viewer, one of steps 2 or 3 is missing or incomplete.

Complete step 3 before the first sign-in

On first sign-in the application writes its own user_accounts row using the role it resolved from metadata, defaulting to Viewer. Running step 3 afterwards corrects it, but setting only the metadata afterwards does not, because the cached Viewer row already exists.

5.3 How the role is resolved, and why it can silently be Viewer

Two independent systems must agree, and neither reads the other:

SystemReads fromConsequence
Dashboard interfaceAuthentication metadata on the signed-in userDecides which controls are shown
DatabaseThe token's role claim, then the user_accounts rowDecides which rows are visible

The dashboard tries, in order: user_metadata.role, raw_user_meta_data.role, user.role, app_metadata.role, raw_app_meta_data.role. For a real account, user.role holds the string "authenticated", which is not an application role and normalises to Viewer. If no metadata key is set, the result is Viewer with no warning shown.

5.4 Adding the remaining users

Authentication lives entirely in Supabase. Administration → Users does not create accounts — it manages the role and access of people who already exist in Supabase.

1
Create the account in Supabase

In the Supabase dashboard go to Authentication → Users → Add user, with their email address, a password, and Auto Confirm User enabled.

2
Set the role as App Metadata

On that user, set App Metadata to the role they need:

{ "role": "Survey Operator" }

Valid values are Administrator, Survey Operator, QA Inspector and Viewer. Optionally set User Metadata to the same value, because the interface reads User Metadata first.

3
They appear on first sign-in

The user shows up in Administration → Users automatically the first time they sign in — that is when their directory row is written. Before then there is no row for them. From that point the dashboard manages their role and access.

Two things that catch people out
  • Set App Metadata, not only User Metadata. The database resolves the role from the token's role claim, which Supabase sources from App Metadata. User Metadata alone makes the interface look correct while the database still sees Viewer — the user sees controls they cannot actually use.
  • Disable revokes permissions, not the account. It sets the directory row to Disabled, which migration 0030 resolves to read-only. The Supabase sign-in account still exists. To stop someone signing in at all, remove or disable the user in Supabase.

Grant individual capabilities in Administration → Roles.

6.2 Verifying the security boundary

Tier 1 — always runnable

Run the Section 3.4 queries, then paste and run all of supabase/migrations/0011_security_tests.sql. Its first, second and final sections must complete without raising an exception.

The SQL editor cannot prove the boundary

The Supabase SQL editor runs as the postgres superuser, which bypasses row-level security entirely. Tier 1 proves the migrations applied and that role resolution is wired. It cannot prove that a Viewer is denied.

Tier 2 — a real boundary test

Requires a Viewer test account and a direct database connection:

psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 <<'SQL'
BEGIN;
  SET LOCAL ROLE authenticated;
  SET LOCAL request.jwt.claims = '{"role":"authenticated","email":"viewer@test.local"}';
  select sec.get_app_role();   -- must print: Viewer
  insert into public.project_settings (id, settings)
    values ('rls_probe', '{}'::jsonb);
  -- EXPECT: ERROR  new row violates row-level security policy     => PASS
ROLLBACK;
SQL

The insert must fail with a row-level-security error. If it succeeds, the boundary is broken — stop and resolve before go-live. Then repeat with an Administrator token and the same statement: that one must succeed.

7Cloudflare Tunnel

Exposing the on-premises services to the dashboard without opening any port to the internet.

The dashboard is served over HTTPS from Cloudflare's edge. Your on-premises services sit on a private network. Cloudflare Tunnel bridges the two: cloudflared runs on each machine and makes outbound-only connections to Cloudflare.

No inbound firewall rule needed for the tunnel

Because cloudflared dials outward, nothing needs to accept an inbound connection. You may still restrict port 8000 at the firewall so that the services remain reachable only from the local network (Section 11.5).

7.1 Install cloudflared

# Windows
winget install --id Cloudflare.cloudflared

# Linux / macOS — see the Cloudflare downloads page for the current package
# https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/

cloudflared --version

7.2 Create one tunnel per machine

Create a tunnel on each machine that hosts a service: one on the worker PC, and one on each of the four station PCs. Five in total.

# on the worker PC
cloudflared tunnel login
cloudflared tunnel create nas-worker

# on each station PC, using a distinct name
cloudflared tunnel create pc1-agent
cloudflared tunnel create pc2-agent
cloudflared tunnel create pc3-agent
cloudflared tunnel create pc4-agent

login opens a browser to authorise your Cloudflare account. create prints a tunnel identifier and writes a credentials file under ~/.cloudflared/<TUNNEL-ID>.json. Keep that file — it is the tunnel's identity, and the next step references it.

7.3 Write the ingress configuration

Each tunnel needs a configuration file mapping public hostnames to local services. Create %USERPROFILE%\.cloudflared\config.yml on Windows, or ~/.cloudflared/config.yml elsewhere.

Worker PC

tunnel: <TUNNEL-ID>
credentials-file: C:\Users\<USER>\.cloudflared\<TUNNEL-ID>.json

ingress:
  - hostname: nas-api.example.com
    service: http://localhost:8000
  - service: http_status:404

Station PC — repeat on each, one hostname per machine

tunnel: <TUNNEL-ID>
credentials-file: C:\Users\<USER>\.cloudflared\<TUNNEL-ID>.json

ingress:
  - hostname: pc1-agent.example.com
    service: http://localhost:8000
  - service: http_status:404
The trailing catch-all rule is required

cloudflared refuses to start unless the final ingress rule is a catch-all. Keep the - service: http_status:404 line exactly as shown.

If you also want an embedded remote desktop for a station, add a second hostname pointing at your remote-desktop service (commonly http://localhost:5901) — see Section 8.7.

7.4 Point DNS at the tunnel

cloudflared tunnel route dns nas-worker  nas-api.example.com
cloudflared tunnel route dns pc1-agent  pc1-agent.example.com
cloudflared tunnel route dns pc2-agent  pc2-agent.example.com
cloudflared tunnel route dns pc3-agent  pc3-agent.example.com
cloudflared tunnel route dns pc4-agent  pc4-agent.example.com

This creates the DNS records automatically.

7.5 Run it as a service

Both options start the tunnel with the machine.

# Windows — registers a service that starts at boot
cloudflared service install

# then set the service to start automatically in services.msc
# Linux — systemd unit at /etc/systemd/system/cloudflared.service
[Unit]
Description=cloudflared
After=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/cloudflared --no-autoupdate run --token <TUNNEL-TOKEN>
Restart=on-failure

[Install]
WantedBy=multi-user.target
sudo systemctl enable --now cloudflared

The single-line token form is the simplest: in the Cloudflare Zero Trust dashboard, open the tunnel, copy the install command, and run it.

7.6 Verify

curl https://nas-api.example.com/health

An HTTP 401 is the correct answer when no token is supplied — it proves the tunnel is routing and the worker is enforcing its guard:

{ "detail": "Unauthorized." }

Now with the token, which should return the live response:

curl -H "Authorization: Bearer <NAS_WORKER_TOKEN>" https://nas-api.example.com/health

{ "status": "ok", "nas_base": "X:\\nas\\360_images", "worker": "NAS-PC-01" }

7.7 Optional — Cloudflare Access

For an additional gate at the origin, create a Cloudflare Access service token and set CF_ACCESS_CLIENT_ID and CF_ACCESS_CLIENT_SECRET (Section 8.4). The Pages Functions forward them automatically. This is defence in depth on top of the session check, not a replacement for it.

8Cloudflare Pages deployment

Build settings, the hosting constraint, and every variable to set.

8.1 Hosting constraint — read this first

Static-only hosting does not work with this platform

The private API — NAS scans, image previews, station probes, rename and upload — is implemented using the Cloudflare Pages Functions runtime: each handler exports an onRequest function and reads secrets from context.env.

Serving the built folder from nginx, Caddy or plain object storage does not execute those handlers. Under a static-only host:

  • every private API route returns the application's HTML instead of JSON,
  • the interface degrades silently, reporting "unavailable" rather than raising an error,
  • and the session check that guards those routes does not run at all.

Deploy to Cloudflare Pages. A Pages-compatible edge runtime also works. If you must self-host, you need to build and maintain your own Pages-compatible server; that component does not ship with this product.

9NAS layout

The folder structure the services read. Getting this wrong fails quietly, not loudly.

The worker and the agents read the survey filesystem directly. By default, the system follows a standard production stage layout, with built-in adaptive dynamic stage discovery supporting alternative grid folders (e.g. Grid 2, Grid 3), flat stage layouts, custom stage aliases, and environment variable overrides (NAS_STITCH_STAGE, etc.). The recommended production layout is shown below.

9.1 The depth rules

Three different conventions are in play. Mixing them up fails silently.

Stage folderNeeds Project-OUT?Needs Grid 1?Used by
00_Raw_dataNoYesWorker + agent
01_MetadataNoYesWorker
02_BlurringNoNoAgent only
03_StitchingYesYesWorker + agent
04_LightroomNoNoAgent only
05_FinalYesYesWorker
DELIVERABLESNoNoAgent only
Three things that commonly go wrong
  • Grid 1 contains a space. On Linux, confirm the mount preserves it.
  • The run folder name is a join key. It links stitched imagery to its telemetry, so the run folder under 03_Stitching and the run folder under 01_Metadata must be identical. If they differ, coordinates will not be paired to imagery.
  • 02_, 04_ and DELIVERABLES have no depth rule. Their first-level directories are read directly as subgrids.

9.2 Subgrid naming

Use the uppercase GIS form, for example N93E70 or N01E037. The platform applies three different subgrid patterns for three different purposes, and the uppercase GIS form is the only shape that satisfies all three. Lowercase works on the worker but is handled inconsistently by the agents.

9.3 Access rights

AccessRequirement
Read the whole survey treeRequired — worker and all four agents
Write to DELIVERABLESRequired — bucket upload
Write to panoramas/Only for the rename action

10.1 Install

copy .env.example .env          # Windows PowerShell

# and any path escaping it is rejected with HTTP 400.

python -c "import secrets; print(secrets.token_urlsafe(48))"

10.3 Run

11.2 Install

Dependencies are a web framework, a server, a configuration loader and process-inspection. The process library matters:

Install the process library even though the service starts without it

Without it the agent cannot detect workstation processes, so the multi-station board never leaves "awaiting agent", and per-station CPU, memory and disk telemetry is absent. The service still runs, so the failure is silent.

Optional GPU telemetry

To show GPU cards on the PC monitoring screen, install the GPU bindings as well — they are not in the requirements file:

.\.venv\Scripts\python -m pip install pynvml

This needs a vendor GPU driver. Without it the card falls back to a browser-reported approximation.

copy .env.example .env

# The NAS root AS MAPPED ON THIS PC (drive letter or UNC path).

.\.venv\Scripts\python app.py

curl http://localhost:8000/health
{
  "status": "ok", "agent_version": "1.0.0", "station_id": "stitch",

11.5 Firewall

The agent binds port 8000 with no transport encryption of its own. Restrict it to the local network:

New-NetFirewallRule -DisplayName "GeoSphere Station Agent" `
  -Direction Inbound -LocalPort 8000 -Protocol TCP `
  -Action Allow -Profile Domain

The Cloudflare Tunnel is outbound-only and needs no inbound rule.

14Known limitations

Product defects that affect a client installation. Read before go-live.

14.1 Station addresses must be set before the board is useful fixed

Impact. Until each station has an address saved, the flight board reports that station as "Unconfigured", the rename action is unavailable for it, and bucket upload for non-Supabase providers cannot run for it. A station without an address does not affect the rest of the board, so PCs can be brought online one at a time.

Resolution. Earlier revisions had no screen for this and required a settings-table SQL update, and a settings export silently dropped the address and port keys. Both are fixed: set the addresses in Settings → Project & Map Settings → 4. Production Pipeline & Workstations (Section 12.4), and the stored settings type now declares those keys. No migration is required when upgrading.

14.2 Bucket upload works for all cloud providers fixed

Resolution. In earlier revisions, chained shell operators caused CLI invocations to fail on non-R2 providers. Station Agent (station-agent/app.py) now executes commands in structured sequential (argv, desc) loops with error trapping, supporting all 7 backends: Cloudflare R2, AWS S3, Wasabi, Google Cloud Storage, Azure Blob, Supabase CLI, and NAS local copy.

14.3 Bucket gate verification supports multi-cloud & pagination fixed

Resolution. The Cloud Bucket Gate (BucketPublicationGate.tsx) now features an automated pagination loop (up to 1,000 objects per page) for Supabase Storage, and multi-cloud candidate detection for Cloudflare R2, AWS S3, and Wasabi deliverable files.

14.4 The in-app tour and help text are out of date

Impact. The first-run interactive tour and the help dialog still describe the pre-refactor interface. They will mislead operators and new staff.

Workaround. Dismiss the tour and train against this guide instead.

14.5 Session inactivity lockout in embedded 360 viewers fixed

Resolution. In earlier revisions, user interactions inside WebGIS and PhotoSphereViewer iframes were invisible to parent window event listeners. An activity bridge in src/App.tsx now listens for window.blur and bidirectional geosphere:activity events, resetting the timeout during active inspection.

14.6 Deletion approval is an interface guard

Impact. The delete capability is granted at the database level to both Administrator and Survey Operator, so the approval queue can be bypassed with a direct API call.

Workaround. Do not grant the Survey Operator role where your process requires approval.

14.6b Disable revokes permissions, but not the sign-in account

Impact. Disable in Administration → Users sets the directory row to Disabled. Since migration 0030 that resolves to read-only at the database level, so the control genuinely revokes.

It does not remove the person's Supabase sign-in account. They can still sign in; they simply see nothing they are not permitted to see. There is deliberately no delete control in the dashboard — deleting the row would leave no record of the revocation, and role resolution would fall back to the token claim, restoring the elevated role.

Workaround. To stop someone signing in at all, remove or disable the user in Supabase → Authentication → Users.

VITE_BRAND_CONTRACT_CODENoSeeded contract code on a fresh install
VITE_BRAND_CLIENT_NAMENoSeeded client name on a fresh install

Rebranding a deployment

The six VITE_BRAND_* variables replace the product name, the browser tab title, every generated report and PDF footer, and the canonical / Open Graph / Twitter / JSON-LD metadata. Logo artwork is not covered — overwrite public/branding/ at deploy time if you need your own.

All six default to the shipped values, so leaving them unset reproduces the default build exactly. Blank means “not configured” for five of them; VITE_BRAND_MARK is the exception, where an empty value is the instruction to omit the mark.

They are build-time — Vite inlines them into dist/, so changing them requires a rebuild, not a settings edit. Same constraint as VITE_SUPABASE_URL: one build per deployment. The three seeded values are only what an untouched install shows before anyone logs in; Admin Settings writes them to the database, and the database wins.
